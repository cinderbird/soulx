# soulx-aim-reticle

불안정한 인식 입력 위에서 조준 인터랙션을 만드는 프로젝트입니다.
소울엑스 사전 과제 **B — 카메라 앞 대상에서 동작하는 반응형 인터렉티브**
제출물입니다.

## 무엇을 만들었나

카메라와 손 인식을 실제로 붙이는 대신, **마우스를 대상의 실제 위치로 쓰고
그 위에 인식 오류를 얹는** 구조로 문제를 재현했습니다.

이렇게 하면 사용자가 의도한 지점을 항상 알 수 있습니다. 그래서 인식 장치가
어떤 오류를 내든 각 처리 단계가 그 오류를 얼마나 줄였는지 **수치로** 잴 수
있습니다.

영상 링크: https://drive.google.com/file/d/1spM60Z9zLwY41F16odAgJ2QFPPZCiRLW/view?usp=drive_link


```
실제 위치(마우스)
  → 인식 오류 얹기
  → 속도 검사      말이 안 되는 좌표를 버린다
  → 대상 선택      여러 후보 중 추적 중인 대상을 고른다
  → 확정 판단      몇 번 맞아야 인정하고 몇 번까지 기다릴지
  → 게인 제어      신뢰도가 낮으면 일부만 따라간다
  → 데드존         의도로 보기 어려운 미세한 이동을 무시한다
  → 보정           One Euro Filter
  → 화면
```

인식 · 처리 · 화면의 세 계층으로 나눴고, 각 계층은 따로 테스트한 뒤
연결했습니다.

## 실행

```bash
npm install
npm run dev        # http://localhost:5173
npm run test       # 106개 테스트
npm run typecheck
npm run build
```

오른쪽 패널에서 상황을 고르거나, "직접 조준해 보기"를 선택해 인식 오류를
직접 켜 보며 마우스로 조준할 수 있습니다. 왼쪽 위 범례가 화면에 보이는 각
점의 뜻을, 왼쪽 아래 지표판이 평균 오차와 반응 속도를 실시간으로 보여줍니다.

## 과제가 요구한 네 가지 비정상 상황

드롭다운에서 바로 재생할 수 있습니다. 같은 경로와 같은 난수를 쓰므로 매번
같은 오류가 같은 시점에 나옵니다.

| 상황 | 무엇을 재현하나 | 무엇을 보게 되나 |
|---|---|---|
| ① 탐지 대상 소실 | 대상이 빠르게 움직이면 인식이 끊긴다. 한 번 끊기면 여러 프레임 이어진다. | 조준점이 사라졌다 나타나기를 반복한다. 8프레임까지는 마지막 위치를 유지하고, 넘어서면 "손을 놓쳤습니다"가 뜬다. |
| ② 탐지 대상 증가 | 실제 대상과 함께 엉뚱한 곳이 손으로 잘못 인식된다. | 조준점이 빨간 점(오검출)에는 전혀 끌려가지 않고 움직이는 실제 대상만 따라간다. 평균 오차가 0에 가깝게 유지된다. |
| ③ 뒤바뀜 | 인식 순서를 바꿈으로써 값이 변경되는 것을 구현한다. | 순서 대신 위치로 고르기 때문에 아무 일도 일어나지 않는다. 목록 첫 번째를 믿는 코드였다면 조준점이 두 위치를 오갔을 상황이다. |
| ④ 먹통 | 카메라가 프레임 자체를 보내지 않는다. | 대상이 화면 밖으로 나간 것과 구분해 "카메라가 멈췄습니다"를 띄운다. 사용자가 해야 할 일이 다르기 때문이다. |

## 주요 판단

채택하지 않은 대안과 그 이유까지 포함한 자세한 내용은
[`docs/adr/`](docs/adr)에 있습니다.

| 판단 | 왜 | 대신 검토했던 것 |
|---|---|---|
| 마우스를 대상의 실제 위치로 쓴다 | 의도한 지점을 항상 알 수 있어 오차를 수치로 잰다 | 실제 웹캠 인식 — 같은 상황을 재현할 수 없다 |
| 인식 오류를 다섯 가지만 만든다 | 과제가 요구한 네 상황을 모두 재현할 수 있는 최소 집합 | 좌우 반전·화면 경계 잘림·신뢰도 하락 — 쓰이지 않을 오류다 |
| 떨림을 이어지는 형태로 만든다 | 실제 인식 오차는 한쪽으로 치우친 채 몇 프레임 이어진다 | 매 프레임 독립적인 노이즈 — 그 성질을 재현하지 못한다 |
| 놓침을 여러 프레임 지속시킨다 | 흔들린 영상은 한 프레임만 망치지 않는다 | 프레임마다 독립적인 확률 |
| 속도 검사와 대상 선택을 나눈다 | 하나는 물리적 한계(절대), 하나는 추적 중인 대상인지(상대)를 본다 | 한 단계로 합치기 — 성격이 다른 판단이 섞인다 |
| 순서 대신 위치로 대상을 고른다 | 인식 결과의 순서는 보장되지 않는다 | 목록 첫 번째 사용 · 다중 가설 추적(이 규모엔 과하다) |
| 5번 중 3번으로 확정하고 8프레임까지 기다린다 | 한 프레임의 우연으로 화면이 흔들리지 않게 한다 | 즉시 확정·즉시 포기 — 빠른 움직임마다 깜빡인다 |
| 누적 이동거리로 끌림을 감지하지 않는다 | 완만한 끌림과 빠른 스와이프가 구분되지 않아 오탐이 더 많다 | 만들기 전에 따져보고 뺐다 |
| One Euro Filter의 파라미터를 다시 잡는다 | 흔히 쓰는 값은 픽셀 좌표 기준이라 정규화 좌표에서는 거의 안 걸린다 | 기본값 사용 · 칼만 필터(튜닝 비용이 크다) |
| 신뢰도가 낮으면 일부만 따라간다 | 오검출이었을 때의 튐을 줄이고 실제였을 때는 몇 프레임 안에 따라잡는다 | 그대로 믿기 · 완전히 무시하기 |
| 못 찾음과 카메라 멈춤을 나눈다 | 사용자가 해야 할 일이 다르다 | "신호 없음" 하나로 처리 |
| 화면이 처리 과정을 보여주게 한다 | 잘 막고 있는 상태와 아무 일도 없는 상태가 화면에서 같아 보이면 안 된다 | 지표 숫자만 늘리기 · 후처리 효과로 꾸미기 |

## 구조

```
src/
  sim/         인식 장치 흉내 — 실제 위치에 오류를 얹는다
  aim/         마우스 위치를 정규화 좌표로
  pipeline/    처리 단계 — 속도 검사 → 대상 선택 → 확정 판단 → 게인 → 데드존 → 보정 → 상태
  metrics/     평균 오차 · 멈췄을 때 떨림 · 반응 속도
  scene/       Three.js 화면 — 조준면, 조준점, 마커, 경로, 배경
  ui/          제어판 · 지표판
```

`pipeline/` 아래 각 모듈은 독립적으로 테스트되고 `main.ts`가 순서대로
연결합니다. 좌표계는 모든 계층에서 -1 ~ 1로 정규화된 화면 좌표로 통일되어
있고, 3D 월드 좌표로의 변환은 화면에 그리기 직전 `AimSurface` 한 곳에서만
일어납니다. 그래야 좌표 문제가 생겼을 때 처리가 틀린 것인지 3D 투영이 틀린
것인지 섞이지 않습니다.

## 주어진 시간이 더 있다면

- **끌림 감지.** 누적 이동거리 하나로는 부족합니다. 최근 몇 프레임의 이동
  방향이 얼마나 일관된지를 함께 보면 서서히 오검출 쪽으로 끌려가는 경우를
  잡을 수 있을 것으로 봅니다.
- **대상 선택의 한계 보완.** 오검출 지점이 실제 대상보다 예상 위치에 가까우면
  그쪽을 고릅니다. 여러 프레임에 걸친 궤적 일관성을 보면 구분할 수 있습니다.
- **구현하지 않은 인식 오류.** 좌우 반전, 화면 경계 잘림, 신뢰도가 서서히
  떨어지는 현상.
- **실제 인식 장치 연동.** 지금은 인식 계층 전체가 모형입니다. `RawFrame`과
  `RawObservation` 인터페이스를 그대로 두고 `sim/recognizer.ts` 자리만
  실제 장치로 바꾸면 되도록 경계를 설계했습니다.
- **번들 분할.** Three.js 때문에 번들이 500KB를 넘습니다. 이번 범위에서는
  우선순위가 낮다고 보고 두었습니다.
